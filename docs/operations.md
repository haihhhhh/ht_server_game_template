# 构建、停服和恢复

## 制作发布包

1. 固定模板、框架、协议源、表格源四套源码版本和构建工具版本。按[入门步骤](getting-started.md)依次生成协议、生成配置表、运行 `Build`。任何一步失败都应停止使用这次的制品。
2. 部署相应的 `bin` 程序、该进程的 JSON、game 使用的完整 `tables/exported` 目录，并提供基础服务连接和进程凭据。协议和配置表生成的 Go 代码已编入程序；运行机只需导出的运行数据和配置。为每份发布包保留源版本和文件摘要。
3. 启动 account、game 和 world 时，模板通过数据库连接上的命名锁串行执行 GORM AutoMigrate。使用带库名的 `HT_MYSQL_DSN` 并授予业务读写及迁移所需的 DDL 权限。回退到旧二进制前，先核对表结构、协议编号和配置表包是否兼容。
4. 发布配套客户端使用同一份协议源生成映射。模板不会在握手时下发业务协议映射，也不校验客户端协议版本。NATS 用户、MySQL 凭据和诊断令牌由运行环境注入。

## 正常停服和升级

先从部署入口停止接纳新用户，让已连接的客户端离开角色并断开，保留 gateway、account、game 和涉及的 world 运行，以便完成已有请求、保存和下线通知。观察日志及待执行数据库任务，再从各进程的本机控制台输入 `stop`。先收尾网关，再停依赖的业务服务，最后停止基础服务。

每个服务的 `stop` 共用 10 秒的 `App.Stop` 上下文。收到操作系统信号时，Pitaya 也可能同时处理退出；正常维护应使用可控的标准输入。进程停止报错时，按日志核对保存、归属和发号节点占用。服务发现里少了一个节点，仅表明它已不在发现列表中，不能据此判定玩家或 Boss 数据已经落库。模板不主动迁移在线玩家。

## 故障后的手工恢复

1. 暂停受影响范围的新请求，保留服务类型、原 `server_id`、分配编号及对应日志。确认旧进程已停止且不会自动重启，并确认它先前发出的 DB 写入均已结束。超时本身不能证明这一点。
2. 在 MySQL 核对对应的账号、角色或 Boss 最近保存的记录。周期保存允许丢失尚未落库的变化；玩家或账号的退出日志可能记录了保存失败。
3. 在 etcd 找到**该范围的精确记录**。业务归属在 `/ht-game/<prefix>/` 下，`account-owners` 指向账号服、`accounts` 指向游戏服、`bosses` 指向公共服务。具体键将 scope 做无填充 URL-safe Base64 编码。比对记录里的 `scope`、`server_id`、`allocation_id` 并记录当前修订号。
4. 只有在确认旧节点和旧写入都不会恢复后，才以 etcd 事务比对该记录的修订号并移除匹配的单条归属。若记录已变更，重新核对，避免误删新分配。恢复流量后，新请求才能重新分配并加载已落库状态。发号节点的占用用[单独的恢复步骤](service-config.md#发号节点-id_node)处理。

无法排除旧节点仍在写库时，应继续隔离受影响范围。归属登记本身不能阻止已发往数据库的旧写入。需要从备份恢复时，先在独立库还原，核对迁移版本和关键数据，再决定切换范围。

## GM 调整业务时间

所有服务使用同一环境的 etcd 和 `prefix`，各机器的系统时间也应保持同步。在任意服务的本机控制台输入：

| 命令 | 效果 |
| --- | --- |
| `clock` | 显示本机系统时间、业务时间及当前偏移。 |
| `clock offset 24h`、`clock offset -30m` | 将偏移设置为指定值，重复操作不会叠加。 |
| `clock set 2030-01-01T08:00:00+08:00` | 按发令机器的系统时间计算偏移，目标时刻必须带时区。 |
| `clock reset` | 恢复零偏移。 |

偏移保存在 `/ht-game/<prefix>/clock/offset`。发令进程在写入成功后应用，其他进程通过订阅跟进。启动时会读最新值，暂时失联的进程使用最后已知偏移。诊断结束后记得执行 `clock reset`。

角色的业务日期随偏移改变。玩家 Tick、保存间隔和在线时长按实际经过的时间计算，向后调时间不会暂停下一次 Tick。RPC 超时、心跳、日志时间和雪花 ID 使用独立的时间基准。需要防止重复领取的每日奖励，由项目按业务日记录领取状态。
