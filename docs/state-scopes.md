# 玩家和公共状态由谁处理

一个账号同一时间在 game 中只运行一个角色。玩家循环持有角色、背包、挑战次数等个人状态。世界 Boss 按逻辑区另设负责人，game 通过内部 RPC 访问。这样同区玩家可以分布在不同 game 节点，也能攻击同一个 Boss。

## 玩家进入、请求和退出

1. 网关登录关联现有 game，找不到归属时等到显式 `Enter` 再分配。候选 game 先预留本地容量，再条件登记归属；竞争失败可以返回现有负责人。节点失联后正式归属仍保留。
2. `PlayerManager.Enter` 建立玩家循环，选角、加载各模块并恢复组件。新进入的请求只有在绑定仍有效且玩家加载完成后才能执行业务。重复进入同一在线角色会返回当前状态，不重复执行组件的进入回调。
3. 普通请求从 game 本地绑定找到已在线玩家。入队前及开始执行时检查连接与分配编号，业务方法在玩家循环中执行。同一玩家的请求与 Tick 顺序运行。进入、替换、退出另需处理节点归属。[入队检查](../servers/game/internal/player/call.go)
4. 默认每秒执行业务 Tick，每 10 秒尝试保存一次。调度使用真实经过时长，给组件传入服务的业务日期。慢请求跨过多个 Tick 时只执行一次。每个玩家默认允许排队 64 个任务，排队数据按估算值限制为 1 MiB，game 默认最多 128 个在线玩家。[调度](../servers/game/internal/player/tick.go) · [game 配置](../configs/game.json)
5. 替换连接保留原循环和内存。真正下线或明确离开角色时，game 停止接收新任务，等循环停止，再提交剩余变化并等之前已提交的保存。保存失败或超时会记录，仍可释放归属。原分配的条件删除失败会在后台重试。[退出任务](../servers/game/internal/handler/player_exit.go)

## 一次计算要用几份数据

能在同一玩家循环完成的操作直接调用同一玩家的组件。例如背包校验并扣道具，再调用角色组件增加经验；整个内存操作期间没有其他玩家任务插入。[代码流程](business-request-flow.md)

需要公共状态时，玩家循环先做个人校验，再定向调用公共负责人。示例中 world 收到攻击后串行扣血，成功回复后 game 扣玩家的次数。等待远端期间，这个玩家的后续请求会等待。公共服务不能同步回调正在等它的同一玩家循环。远端已经扣血但回复丢失时，两份状态可能只更新一份。双方定期保存也可能分别成功或失败。[世界 Boss 示例](public-service.md)

增加 game 能接纳新分配的玩家，增加 world 能接纳新分配的 Boss。同一在线玩家和同一热点 Boss 仍由各自原节点处理。人工处理归属前，先确认旧进程已经停止，且旧的保存任务不会继续写入。[运行手册](operations.md)
